### 5.1 同一实体 3~4 套并行实现 ★ P0

**修复方案（终极目标）**：

2. GameMemory 降级为运行时累积层（保留 history/accessCount/dormantSince 等运行时字段），通过订阅 StateManager 变更更新派生视图，**不再独立持久化**
3. gameState 旧字段全部转为只读派生视图（由 `_syncLegacyMirror` 单向同步）
4. phone-ui.js 全部改读 StateManager.get(...) 或通过响应式订阅

### 5.2 `GameMemoryAdapter` 反而引入第三数据源 ★ P1

`state/adapters/game-memory-adapter.js:9-70` 订阅 StateManager 变更，把 `entities.bag/quests/characters/locations/events` 单向同步到 `GameMemory.tables`，制造了**第三份角色/物品/任务数据**。

且 `syncToGameMemory`（34-53 行）每次 entities 变更都**全量重建** `tables.items/characters/locations` 三个 map，**丢失 GameMemory 在这些对象上维护的运行时字段**（`dormantSince`/`lastMentioned`/`accessCount`/`history`/`locked` 等）。

**修复方案**：

1. `GameMemory.tables` 改为 StateManager 数据的只读视图（getter 派生，不持久化）
2. 运行时累积字段（`history`/`accessCount` 等）单独存储在 `GameMemory._runtime` 字典，keyed by entity id
3. 删除 `GameMemoryAdapter`（adapter 未起到隔离作用）

### 5.3 `_syncLegacyMirror` 框架级双写 ★ P1

`state-manager.js:137-172` 每次 `set` 都同步写旧字段，使 `gameState.allCharacters`/`currentBag`/`currentQuests`/`keyEvents`/`gameTime`/`_stats.totalTurns` 等旧字段与新路径**永久并行存在**。

`schema.js:141-148, 153-157, 162-168` 内 3 处特殊转换暴露新旧 schema 形状不兼容：

- `entities.characters`（数组）↔ `allCharacters`（按 name 索引的对象）
- `progress.turn` → `_stats.totalTurns`（嵌套路径，需特判）
- `entities.events`（对象数组）↔ `keyEvents`（字符串数组，需 `e.content` 提取）

**修复方案**：

1. 短期：保留 `_syncLegacyMirror` 但明确标注"仅 UI 层读取，不可写入"
2. 中期：phone-ui.js 全部改读 StateManager.get
3. 长期：删除 `_syncLegacyMirror` 与 gameState 旧字段

### 5.4 `_legacyMode` 开关是摆设 ★ P2

`state-manager.js:11` 字段 `_legacyMode: true` 注释"迁移期间允许 getLegacy/setLegacy"，但无任何代码读取此标志，也无切换为 false 的路径。迁移开关是摆设，双写将永久开启。

**修复方案**：要么定期检查迁移进度并切换，要么删除此字段。

### 5.5 `longTermMemory` getter 混用引用/快照语义 ★ P1

`tavern-compat.js:3550-3564` getter 返回的 `result` 对象中：

- `characterTable`/`itemTable`/`locationTable`/`importantEvents`/`activeQuests`/`timeline`：对 `self.tables.*` 的**实时引用**（外部写入会改到真实数据）
- `worldAnchors`：**新建快照数组**（3541-3543，写入不影响源）
- `masterSummary`：**计算快照**（getter 每次重新拼接）

`game.js:2517-2586` 通过 `longTermMemory.characterTable[name] = {...}` 写入实际作用于 `self.tables.characters`，而 `longTermMemory.worldAnchors.push(...)` 不会写回源。**语义不一致**。

**修复方案**：统一为只读快照（每次返回新对象），写入必须通过 GameMemory 显式 API。

### 5.6 `_worldNotes` 不持久化（数据丢失 Bug）★ P0

`tavern-compat.js:3547`（getter 内懒初始化）+ `3562`（暴露为 `worldNotes`）+ `phone-ui.js:828`（`EnhancedMemory.longTermMemory.worldNotes.push({...})` 写入）。

## 六、性能问题

### 6.1 `longTermMemory` getter 每次访问重建数组（高频热点）★ P0

`tavern-compat.js:3537-3573` getter 每次访问都：① 新建 `worldAnchors` 数组并遍历**所有** `permanentFacts` 键及其条目做映射（3541-3543）；② 新建 `result` 对象；③ 在 `result` 上再 `Object.defineProperty` 注册 `masterSummary` 访问器（3567）。

`game.js:2517-2530` 与 `2571-2586` 在循环内**逐字符/逐条**访问 `EnhancedMemory.longTermMemory.characterTable[name]`，每次访问都触发上述重建。

**复杂度**：每次属性读取为 O(全部 permanentFacts 条目数)；在 game.js 循环中累计为 O(循环次数 × 永久事实总数)。

**修复方案**：缓存 `longTermMemory` 返回值，仅在 permanentFacts 变更时失效缓存。

### 6.2 `getStats` 全量 JSON 序列化 ★ P2

`tavern-compat.js:3389-3391` `getStats` 返回 `memorySize: JSON.stringify(this).length`，对整个 `GameMemory` 实例做 `JSON.stringify` 仅为取字符串长度。该函数在 `MemoryManagerUI.renderOverview`（3824 行）每次渲染概览页时调用。

**修复方案**：缓存 `memorySize`，仅在 saveToStorage 时计算。

### 6.3 `extractStr`/`extractArr`/`extractObj`/`extractObjArr` 每次调用都 `new RegExp` ★ P2

`core.js:2562, 2591, 2641, 2660` 这 4 个函数被 `game.js` 解析 AI 响应时多处调用（`game.js:1883, 2158, 2163, 2180, 3936, 3939`），每次都重新构造 RegExp 对象。`escapeRegExp`（2559）也在每次调用时跑一遍 `replace`。

**修复方案**：缓存常用 field 的 RegExp（用 Map 缓存 `escapeRegExp(field)` + 正则字符串）。

### 6.4 `GameLinker.refreshByDataChange` 的 rAF 调度对空 `_refreshers` 反复触发 ★ P2

每次调用都会 `Object.keys(self._pendingPages)` 后再 `self.refresh(page)`，`refresh` 内 `var fn = this._refreshers[pageName]; if (fn)` 对空对象查询。全代码库 25 处调用累积起来，每次数据变更都启动无意义的 rAF + 空对象遍历。

**修复方案**：删除 GameLinker 整套系统（见 2.2）。

### 6.5 `injectTheaterToLogs` 内 `mods.findIndex` 在循环中 ★ P2

`core.js:3341-3348` 对每个 theater key 都 `mods.findIndex(...)` 线性扫描整个 `mods` 数组。当 worldModules 较多 + 单次 AI 响应包含多个小剧场时，是 O(n²)。

**修复方案**：先把 `mods` 转为 Map（key 为 theater key），后续查找 O(1)。

### 6.6 `parseSSEEventText` 同一 rawBody 可能被解析两遍 ★ P3

`core.js:4712-4750` 流式 SSE 每条 `data: {...}` 都 `JSON.parse` 一次。但 `parseAIResponseFallback`（4758-4802）兜底时又对 `rawBody` 整体 `JSON.parse`（4762）+ 用正则 `match` 抽所有 data 行再次逐条 `JSON.parse`（4790-4797）。

**修复方案**：兜底路径直接用流式累积的结果，避免二次解析。

### 6.7 `phone-ui.js` 大量 `document.getElementById('logSubContent')` 重复调用 ★ P3

`toggleMomentLike` / `showMomentCommentInput` / `sendMomentComment` / `buyShopItem` / `renderWorldModules` 等多函数内反复 `getElementById` 查询同一容器，同函数体内多次调用未缓存局部变量。

**修复方案**：函数入口 `const subContent = document.getElementById('logSubContent');` 后续复用。

### 6.8 `renderNpcPage` 直接 innerHTML 拼接未用 DocumentFragment ★ P3

`phone-ui.js:7316-7520` NPC 列表渲染通过字符串拼接 `+=` 累积 HTML 后一次性 `innerHTML =`。对于角色数量较大的场景，字符串拼接成本随数量线性增长。

**修复方案**：使用 DocumentFragment + `createElement` 逐项 append（或保留 `innerHTML` 但用数组 `push + join`）。

### 6.9 `renderPresetPages` 中 scroll 监听无防抖 ★ P3

预设列表滚动监听未做 throttle/debounce，滚动过程中每帧触发回调。

**修复方案**：使用已定义的 `throttle`（utils.js:74，目前死代码）。

### 6.10 `world-preset-chip` / `[data-fontsize]` forEach 内无防重复绑定标记 ★ P3

批量 `forEach` 为每个 chip 添加 `addEventListener`，未使用事件委托也未检查是否已绑定，重复渲染会叠加监听器。

**修复方案**：改用事件委托（在父容器绑一个监听器，用 `e.target.closest('.world-preset-chip')` 定位）。

### 6.11 `worldinfo.js` 缓存键仅用 currentTurn，未包含条目内容版本号 ★ P2

扫描引擎依赖 `gameState._wiCachedResult` / `gameState._wiCachedTurn` 缓存命中逻辑。当条目编辑后未触发 `save` 时（如直接修改内存对象），缓存不会失效；反之频繁 `save` 会反复清缓存。

**修复方案**：缓存键加上 `_wiEntryVersion` 自增计数器，每次条目变更（add/update/delete）递增。

### 6.12 `_harvestAllEntriesToMemory` 启动全量遍历 ★ P3

`worldinfo.js:71-84` `init` 时一次性遍历所有书 + 所有条目调用 `EnhancedMemory.syncWorldInfoEntry`。条目数较多时启动延迟可见，且无去重保护。

**修复方案**：用 `requestIdleCallback` 分批收割，或仅在首次启动时执行并标记 `_harvested = true`。

### 6.13 `getTheaterContent` 巨大 theaterVars 映射每次重建 ★ P3

`modules.js` MacroEngine.getTheaterContent 每次调用构建包含约 20 个键值的大型 theaterVars 映射对象（即使大多数调用只用到少数几个），并执行 `parseTheaterContent` 对 ~20 种标签做正则匹配。

**修复方案**：延迟构造，仅在使用某字段时才填充；或缓存模板，仅 gameState 变更时重建。

### 6.14 `parsePreset` 巨型分支解析 ★ P3

`modules.js` PresetManager.parsePreset 单函数承担 `prompt_order` / `regex_scripts` / `extensions` / `prompts` 数组化的全部解析分支，每次导入/加载都会被调用，函数体过长（数百行），分支判断较多。

**修复方案**：拆为 `_parsePromptOrder` / `_parseRegexScripts` / `_parseExtensions` / `_parsePromptsArray` 等子函数。

### 6.15 `StorageMonitor.getUsedSpace` 遍历整个 localStorage ★ P3

`utils.js:363-377` 遍历整个 `localStorage`，对每个 key 调用一次 `localStorage.getItem(key)` 累加长度。`safeSetItem`（271-293）每次写入前都调用 `checkCapacity`（虽有 30s 缓存但每次仍执行 `getUsedSpace` 全量遍历）。

**修复方案**：维护一个 `localStorage` size 的内存计数器，set/delete 时增减，避免全量遍历。

### 6.16 `DOMCache._evictIfNeeded` 每次插入触发 O(n log n) 排序 ★ P3

`utils.js:42-51` 每次向 `_cache` 写入后即调用 `Object.keys(this._cache)` 全量取键并 `.sort()` 排序以淘汰最旧条目。在写入高频场景下每次插入都触发 O(n log n) 排序。

**修复方案**：用双向链表 + Map 实现 LRU，淘汰 O(1)。

### 6.17 `safeSetItem` 性能开销 ★ P3

每次 `localStorage.setItem` 之前都计算 `(key.length + value.length) * 2` 并调用 `StorageMonitor.checkCapacity()` 以及写入后 `invalidateCache()`。`Storage.set` / `setJSON` 均透传该开销。

**修复方案**：仅对大值（如 > 1MB）执行容量检查，小值直接写入。

### 6.18 NPC 私聊 prompt 大字符串拼接 60+ 次 `+=` ★ P3

`game.js:3822-3884` `requestNpcReply` 中 `systemMsg` 通过 60+ 次 `systemMsg += '...'` 拼接。每次 `+=` 都创建新字符串。

**修复方案**：改用 `['段1', '段2', ...].join('')`。

### 6.19 `_slimAssistantMessage` 频繁 JSON.parse ★ P3

`game.js:428-458` 该函数被三处调用：1178 行（发送前瘦身历史）、1595 行（上下文超限时瘦身）、2210 行（写入历史前瘦身）。每次调用都执行 `JSON.parse(trimmed)`，且 `recent` 数组中的同一消息可能在「发送前瘦身」和「超限瘦身」两阶段被重复 parse。

**修复方案**：用 `WeakMap` 缓存已 parse 的消息，避免重复解析。

### 6.20 `estimateTokensForMessagesUtil` 多次调用无跨调用缓存 ★ P3

`game.js` 内 `estimateTokensForMessagesUtil(messages)` 和 `estimateTokensUtil(msg.content)` 在 sendAIRequest 流程内多次调用：1580 行计算初始 currentTokens，1597/1632 行瘦身/淘汰后递减，2288 行 updateTokenCount 又重新估算整个 conversationHistory，2496-2497 行 _compressConversation 内再算 originalTokens/summaryTokens。无跨调用缓存。

**修复方案**：在 `gameState` 上维护 `_lastTokenEstimate` + 触发版本号，每次 messages 变更时更新。

### 核心问题

1. **最严重架构问题**：状态管理多源真相（同一实体 3~4 套并行存储 + 2~4 个同步函数）
2. **最严重 Bug**：`_worldNotes` 不持久化导致存档丢失数据
3. **最大死代码**：systems.css 1760 行未使用规则（占文件 62%）+ GameLinker 整套联动系统（含 25 处调用点都是 no-op）
4. **最大性能热点**：`longTermMemory` getter 在循环内被反复访问，每次重建数组
5. **最大维护负担**：`core.js` 5520 行 God file 承担 13 个职责 + 与 game.js 双向循环依赖

### 修复策略建议

按"先死后活、先删后改"原则：

1. **先删死代码**（第一阶段 + 第二阶段）—— 零风险，立即降低维护负担
2. **再修正确性 Bug**（第一阶段）—— 防止数据继续丢失
3. **再合并重复**（第三阶段）—— 机械性工作，不改变行为
4. **再收敛多套实现**（第四阶段）—— 改变行为但保持功能
5. **最后做架构重构**（第五阶段）—— 大动作但收益最高

每个阶段完成后应跑一轮回归测试（5 回合游戏），确保功能不回归。
